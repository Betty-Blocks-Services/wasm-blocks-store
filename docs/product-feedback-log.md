# WASM Actions — product feedback log (for Betty Blocks product developers)

Shared, living log of things discovered through hands-on testing of BB's WASM Actions feature that are worth reporting to the product developers who build the platform's WASM tooling itself (Block Store, IDE, Actions Compiler, function.json ingestion, etc.). Newest entries at the top. This is distinct from `developer-learnings-log.md`, which tracks things worth documenting *for* Betty Blocks developers rather than feedback *to* product.

This log started in one person's local learning project and now lives here so it compounds across everyone using this repo — see `../.claude/skills/wasm-actions/SKILL.md` for how findings get logged here going forward, and `../CONTRIBUTING.md` for the discipline around verifying a claim before writing it down as fact (see the entries below marked RETRACTED/corrected for why that discipline exists).

Each entry: what was observed, how it was found, why it matters, and status (open / reported / confirmed fixed).

## NARROWED, still unresolved: a custom Wasm step became permanently un-addable to any action after deletion — host-imports hypothesis ruled out, points at something app/registration-specific (2026-08-10)

**Observed:** Marcel deleted a wizard-uploaded "Slugify Text" custom step registration from the `marcel-tes` app's Wasm steps palette (via the wrench/settings icon shown on hover, tagged "Application specific"). From that point on, **every attempt to add a "Slugify Text"-shaped step to any action's canvas in this app fails** with "Oops! Something went wrong — Failed to create action step. Refresh the page and try again" (which, on retry, degrades further into "The step you're looking for doesn't exist (anymore)").

**Full elimination chain — every one of these was tried, live, and failed identically:**
1. Plain `bb functions publish` re-publish of the exact same `slugify-text` 1.0 function, no changes.
2. A hard version bump to `2.0` (fresh directory, `wit/world.wit`/`Cargo.toml` version strings updated) — same failure.
3. Changing `function.json`'s `category` from `"Text"` to `"String Functions"` — same failure.
4. A full rename to a genuinely new function name (`make-slug`: new folder, `Cargo.toml` package name, WIT package/interface name, lib.rs bindings path, published as `makeSlug-1.0`) — same failure, ruling out a name-level tombstone.
5. Rebuilding the `.wasm` from source for real (installed the local Rust + `wasm32-wasip2` toolchain at `~/.cargo/bin`, confirmed a genuinely different checksum and valid component encoding, all 12 unit tests passing) — same failure, ruling out "it was always the same stale binary."
6. Renaming the WIT **world** away from `main` — produced a **byte-identical** binary (confirmed via `git hash-object`), proving the world's name isn't embedded in the compiled component at all; not a usable lever.
7. Changing the function's actual return type from a bare `string` to `result<string, string>` (matching `store-file-base64`'s shape) — a genuinely different structural signature, confirmed via a new checksum — **still failed identically.**

**Isolated to something about this specific component/shape, not the action, not concurrent editing, not any label:** throughout all of the above, in the same action, in the same browser session, with no other tab open, `store-file-base64` (a different custom step, never deleted, never touched) continued to drag onto the canvas and open for configuration with **zero errors** every single time. This rules out the action itself, session/auth state, and general platform load as explanations.

**Remaining, untested hypothesis:** the one structural dimension never varied across any attempt is **host imports** — every slugify/make-slug variant had zero; `store-file-base64` has five (`wasi:http`, `wasi:random`, `data-api`, `upload-file`, `types`). This raises the possibility that this is the same underlying `actions_compiler#internal_error: Not yet healthy` backend issue documented elsewhere in this log, just surfacing at step-*creation* time instead of compile time, and specifically affecting zero-import components. Testing this would require vendoring a real host WIT dependency into a from-scratch component — a meaningfully bigger step than anything tried above.

**Decision: pausing here.** Every lever available from the client side (WIT authoring, `function.json`, CLI publish, rebuilding, renaming at every level) has been tried and eliminated. Continuing would mean guessing at backend internals with no server-side visibility. This is now a strong candidate to report directly to Betty Blocks product/support, with this full elimination chain as evidence, rather than continue guessing.

**Current state left behind:** `marcel-tes`'s `[calc] Webuser Full Name` action has no "Slugify Text"/"make-slug" step in its canvas (removed after each failed attempt) and no `Store File Base64` step either (removed earlier per a separate, still-open compile-hang investigation above). Both `store-file-base64` and `make-slug` remain published and validated in the local `marcel-tes` CLI project; `make-slug`'s registration is simply unusable in this app until/unless Betty Blocks resolves whatever this is.

**How found:** while trying to restore a `slugify-text` step that had worked fine earlier in the same session, after Marcel deleted what he believed was only a stale, superseded wizard-uploaded registration; escalated through version → category → rename → real rebuild → world rename → return-type change, each retested live and each failing identically.

**Update, 2026-08-10 — host-imports hypothesis tested and ruled out.** To test the leading hypothesis without the confound of `make-slug`/`slugify-text`'s reuse history, removed `make-slug` entirely from the `marcel-tes` CLI project and, in its place, ported `generate-uuid` verbatim from `block-store-wasm-components-main` (adapted only to marcel-tes's standalone-crate style, matching how `make-slug` itself was structured) — a genuinely fresh function name, never before registered in this app, with **zero host imports**, same as every broken `make-slug`/`slugify-text` variant. Built (`cargo test`, `cargo build --release --target wasm32-wasip2`, component header confirmed `0d 00 01 00`), published via `bb functions publish`, and dragged onto an action canvas: **it worked, first try, zero errors** — indistinguishable from `store-file-base64`'s success.

**Conclusion:** zero host imports is not, by itself, what breaks step-creation — a fresh zero-import component works fine. The failure is specific to `make-slug`/`slugify-text` itself, most likely tied to its reuse of a name/registration lineage that once had a wizard-uploaded "Slugify Text" step deleted from the app's palette (see the original elimination chain above, which already ruled out a simple name-level tombstone via the `make-slug` rename — but a rename alone may not have been enough to escape whatever server-side state keys off something else in that lineage, e.g. an internal ID, a stale Block Store record, or the specific `application_id` + function-identity pairing). Root cause is still not identified, but the search space has narrowed from "any zero-import component in this app" down to "something specific to this one function's history in this one app."

**Status:** narrowed, still unresolved on root cause — worth reporting to Betty Blocks now with both the original elimination chain and this new negative result (a fresh zero-import component works fine), since it rules out the platform-wide explanation and points at something app/registration-specific instead.

## Second, distinct "Actions compiling..." hang — this time on a CLI-published (app-scoped), fully-configured `store-file-base64` step (2026-08-10)

**Observed:** after saving the CLI-published `store-file-base64` step (see the resolved Model/Property entry below) with real values wired into every field (MODEL=`Webuser`, PROPERTY=`file`, BASE64 DATA/FILENAME/FILE EXTENSION/FILE REFERENCE all filled), the header's "Test run" and "Logs" buttons both went into their disabled state with the tooltip **"Actions compiling..."** and stayed there for 90+ seconds across a full page reload — never resolving, matching the pattern (though not the specific trigger) of the earlier `create-record`/`world main` compile hang logged elsewhere in this file.

**Why this looks like a different trigger, not the same bug recurring:** the earlier hang was root-caused precisely to a WIT world named `main` combined with a host import — `store-file-base64`'s WIT world is named `store-file-base64`, not `main`, so that specific fix doesn't apply here. The step is also otherwise identical to the same component tested earlier via the interactive wizard (which compiled fine, just with the synthetic Model/Property fallback) — the two variables that changed between "compiled fine" and "hangs" are (a) it was published via `bb functions publish` this time, landing as an "Application specific" step rather than a wizard-uploaded one, and (b) MODEL/PROPERTY are now bound to real schema references (`Webuser`/`file`) instead of unset/synthetic values. Not yet isolated which of these two (or something else entirely) is the actual trigger.

**Why it matters:** this is now the *second* distinct trigger found for the same class of "actions_compiler" hang, suggesting the underlying health-check/compile service has more than one failure mode, or that real Model/Property references (now that they finally work) exercise a code path the compiler doesn't handle well yet.

**How found:** immediately after saving the fully-wired `store-file-base64` step, while trying to actually Test run it per the original goal of validating the whole upload flow end to end.

**Update, 2026-08-10 — rules out "CLI-published/app-scoped" as the trigger.** Cleaned up the app to consolidate both custom steps onto the CLI publish path: republished `slugify-text` via `bb functions publish` (previously wizard-uploaded), deleted the old wizard-uploaded instance from the canvas, and swapped in the CLI-published one with identical config. Saved — **the same "Actions compiling..." hang recurred immediately**, even though now *both* custom steps in the action are CLI-published/app-scoped, with no wizard-uploaded component left in the flow at all. This rules out "CLI-published vs. wizard-uploaded provenance" as the trigger. The remaining candidate is the real Model/Property references on `store-file-base64` (`Webuser`/`file`) — not yet isolated by removing/re-adding just that binding, but now the leading hypothesis by elimination.

**Update, 2026-08-10 — concrete error message finally captured, and it survives removing Slugify Text from the flow entirely.** While diagnosing a separate multi-tab confusion (see the new entry below), ended up with two browser tabs showing genuinely different, out-of-sync canvases for the same action — one still had `Slugify Text` in the flow, the other had already lost it (deleted during our overlapping edits). Refreshing both via a real in-app navigation (not a raw reload) synced them to the *true* current canvas: **`Start → Expression → Store File Base64 → Update Record → Finish` — no Slugify Text at all** — and the header still showed the persistent error state. Hovering it revealed the exact same backend error as the original `create-record` hang: **"Failed to compile actions. Error: ** (ActionsCompiler.CompileError) actions_compiler#internal_error: Not yet healthy."** Since this reproduces on a simplified 4-step canvas with `Slugify Text` completely absent, it isolates the trigger further: **it's specific to `store-file-base64`'s real `Webuser`/`file` Model/Property binding, not to Slugify Text, not to step count, and not to CLI-vs-wizard provenance.**

**Status:** open — not yet reported to product devs. Concrete error message confirmed reproducible with `Webuser`/`file` as the only variable left unexplained. Next diagnostic step: temporarily clear MODEL/PROPERTY on the CLI-published `store-file-base64` step (or remove the step) and see if the same action compiles cleanly — the last isolation needed to confirm this specific binding is the trigger.

**ROOT CAUSE CONFIRMED, 2026-08-12 — via Betty Blocks' own product team.** BB product replied with a wasmCloud host log line captured for this exact hang:
```
failed to link components, unbinding all plugins error=failed to pre-instantiate during component linking
Caused by:
  0: component imports instance `betty-blocks-utilities:upload-file/upload-file`, but a matching implementation was not found in the linker
  1: instance export `upload` has the wrong type
  2: function implementation is missing
```
Their diagnosis: the host-capability `upload-file` WIT interface was updated (renamed/versioned `betty-blocks-utilities:upload-file` → `betty-blocks-types:upload-file@3.0.0`) and `store-file-base64`'s example was never updated to match — confirmed independently by cloning `bettyblocks/wasm-base-components` and diffing its current `wit/upload-file/upload-file.wit` against the vendored copy in both `block-store-wasm-components-main` and `marcel-tes`: the `input` record's `file-bytes: list<u8>` field was replaced with `file-base64: string` (host now decodes base64 itself, explicitly to avoid a `list<u8>` memory blowup that traps around 2.67 MiB per the new interface's own comment), and `model`/`property` were renamed to `betty-model`/`betty-property`. So **it's not an app-specific/registration issue at all** — it's real version skew between the shipped example component and BB's own current host capability provider, per BB product's own admission that `block-store-wasm-components` itself needs the same fix. Full technical writeup and the generalization concern (any old-style `betty-blocks-utilities:*` import is a candidate for the same class of failure) logged in `developer-learnings-log.md`'s "ROOT CAUSE FOUND" entry. This resolves the "leading hypothesis" noted below (real Model/Property binding) — it was actually the `file-bytes`/`upload` payload shape, not the Model/Property binding itself, that the linker choked on.

**Status:** RESOLVED, 2026-08-12. Updated the `marcel-tes` copy of `store-file-base64` to import `betty-blocks-types:upload-file/upload-file@3.0.0` instead of the old unversioned interface (full technical diff in `developer-learnings-log.md`'s matching entry), republished via `bb functions publish`, and confirmed live: the step compiles cleanly with real Model/Property values and successfully saves a real file. Worth flagging back to BB product that `block-store-wasm-components`'s own published example is still on the old interface and needs the identical update — otherwise anyone copying it fresh will hit this same hang with no obvious cause.

**Update, 2026-08-10 — component code fully re-confirmed identical between apps, ruling out drift as an explanation.** Diffed every file in `marcel-tes/functions/store-file-base64/1.0/` against `block-store-wasm-components-main/functions/store-file-base64/1.0/` (`Cargo.toml`, `function.json`, `wkg.toml`/`wkg.lock`, `wit/world.wit`, all of `external/*.wit`, the full `wit/deps/` tree, `src/lib.rs`, `tests/mod.rs`): zero differences anywhere. The compiled `.wasm` binaries are byte-for-byte identical (`sha1: 6a75ce7377323e7dc476ba5c2887f82f1f50a57a`, both 100,922 bytes). This closes off "maybe marcel-tes is running a stale or subtly-modified build" as a possible confound — whatever causes the indefinite "Actions compiling..." hang in `marcel-tes` when the step is saved with real Model/Property values, it is provably not a difference in the component itself. Reinforces the existing conclusion that this is a backend/app-state issue (`actions_compiler#internal_error: Not yet healthy`), not something fixable by touching the Rust/WIT source or republishing.

## Editing the same action in two browser tabs desyncs silently — deleted steps surface as "The step you're looking for doesn't exist (anymore)" rather than a clear conflict warning (2026-08-10)

**Observed:** with the same action (`[calc] Webuser Full Name`) open in two separate browser tabs, one tab deleted a step (`Slugify Text`) and added/configured a replacement while the other tab still had the original step selected. The second tab then showed a broken-link-style error page — **"The step you're looking for doesn't exist (anymore) — Looks like you followed a bad link."** — when reopening that step, and a warning triangle on the canvas node itself. Initially this looked like it might be a genuine platform bug (e.g. a naming/versioning collision from re-publishing a Block Store component), but it was actually much simpler: **two tabs silently diverged on the same live action with no realtime sync or conflict warning between them.** A plain reload didn't fix it (re-triggers the already-logged "canvas renders empty on raw reload" bug); only a genuine in-app navigation (via the Actions list) resynced each tab to the true current server state — and even then, the two tabs' "true current state" briefly disagreed with each other (one still showed `Slugify Text` in the flow, the other didn't) until both were independently refreshed via a real link click.

**Why it matters:** for anyone routinely working with a coworker/AI agent on the same action in parallel tabs (a very natural workflow), silent desync plus a generic "bad link" error is confusing and easy to misdiagnose as a data-loss or component-registration bug, when the actual state is fine — it just needs a real navigation, not a reload, to resync. A conflict warning ("this step was deleted in another session, refresh to see the current flow") would be a substantial UX improvement over the bare 404-style page.

**How found:** Marcel and Claude editing the same action in two tabs simultaneously — one console deleting/re-adding a step while the other still had it open, surfacing the "doesn't exist" error and prompting (incorrectly, as it turned out) a hypothesis that the CLI publish/versioning had caused a naming collision.

**Status:** open — not yet reported to product devs.

## RESOLVED: third-party Wasm steps *can* get real native Model/Property selectors — via `bb functions publish`, not the IDE wizard (2026-08-07, resolved 2026-08-10)

**Observed:** added `store-file-base64` (BB's own official example, WIT used verbatim/unmodified) as a step in a real action, originally just to test whether it — like the `create-record`/`world main` bug below — would also compile-hang the actions_compiler. In the process, found its MODEL and PROPERTY options are not bound to real app Data Models at all. Opening MODEL's "Select variable" picker offers only an auto-generated Input variable named `model_Store File Base64_1`. Following the "Based on schema model" link under PROPERTY navigates to `/app/schema-models/<id>` and lands on a literal, real, **read-only Data Model** the platform silently created in the app's own schema, named `property_Store File Base64_1`, with a single property `name: Text (single-line)` — a structural mirror of the WIT record shapes (`record model { name: string }`, `record property { name: string }` from `betty-blocks-utilities:types`), not a reference to any actual table/attribute in the app.

**Why this looks like a platform gap, not a WIT-authoring mistake:** the official example's `function.json` explicitly declares these options as `"type": "Model"` and `"type": "Property"` (the latter with `"model": "model"` for adaptive filtering and `"allowedKinds": ["FILE","IMAGE"]`) — presumably what drives the real native selector UI (pick any app Model → Property list adapts, filtered to file/image kinds) when this ships as a first-party/native step. But the third-party "Add custom Wasm step" wizard never reads `function.json` (see below) — it only introspects the compiled `.wasm`'s WIT interface, which has no vocabulary for "this references one of the app's real Models." It appears to fall back to auto-materializing a synthetic, read-only Data Model matching the record's shape and requiring a bound variable of that exact synthetic type — something no real action can ever produce.

**Open question for product — genuinely unsure which side of the line this falls on:** is there *any* way today for a third-party/Block Store component author to get a WIT parameter treated as a true native Model or Property selector (adaptive, kind-filtered, backed by the app's real schema) — via a specific WIT `resource` type, a naming convention, or some other undocumented mechanism? Or is that UI treatment exclusively reachable through BB's internal `function.json`-driven first-party pipeline, with nothing equivalent exposed to third parties? We haven't found documentation either way, and didn't want to burn more build cycles guessing at an untested `resource`-based variant without knowing if it's even a plausible path. This directly blocks a realistic use case: uploading arbitrary data to a caller-chosen Model's file/image property (reserve space via an upload request, upload the bytes, get back a file reference, assign it in a later Update Record step) — if this genuinely isn't possible for third parties today, we'd like to know that explicitly so we stop trying; if there's a supported way, we'd like to know what it is.

**How found:** while trying to configure `store-file-base64` as a control for isolating a separate `actions_compiler#internal_error: Not yet healthy` compile-hang bug (triggered by our `create-record` step; not yet written up in this log). Marcel recognized the resulting picker as BB's "schema model" construct — a temporary/generated object distinct from real database tables and attributes.

**Update, 2026-08-10 — found BB's own internal roadmap doc, and a second, real publish path that changes the shape of this question.** Marcel shared an internal engineering doc ("Betty Blocks WIT types") mapping WIT constructs to option UI types with a "Supported" checkmark column. It confirms: Model selector, Property selector, Record/Collection/Value/Subaction selectors, Authentication profile, Property mapping, and Variable map are **all currently unchecked/unsupported** for WIT-type inference — this is known, active, ticketed roadmap work on BB's side (one item, WIT Variants input support, is tracked as `PHOEN-954`, status Backlog), not something we're missing. The doc also carries BB engineers' own open question on the `Property selector` row, verbatim: *"depends on does not work, how are we going to do this in WIT? Also, allowedKinds has the same problem."* — i.e. the adaptive Property-list-filtered-by-Model mechanic is an acknowledged unsolved problem internally, not just for third parties.

However, this doc appears scoped specifically to *inferring* these rich types from WIT alone (proposed convention: `betty-model`, `betty-property`, etc. record names) — it doesn't settle whether `function.json`'s already-working `"type": "Model"`/`"type": "Property"` meta (the mechanism real native steps already use successfully) would render correctly if it actually reached the backend through a different ingestion path. That distinction turned out to matter: we found the `@betty-blocks/cli` package (`bb functions publish`) is a **second, genuinely different publish path** for WASM Block Store components, separate from the interactive "Add custom Wasm step" wizard. Confirmed directly from source ([`publishWasmBlockStoreFunctions.ts`](https://github.com/bettyblocks/cli/blob/master/src/functions/publishWasmBlockStoreFunctions.ts)): it reads `function.json` from the function's folder and sends it *together with* the `.wasm` in one multipart POST to `{blockstoreApiUrl}/blocks/publish?type=wasm-function` — a different backend endpoint than the interactive wizard, and one that actually receives `function.json`, unlike the wizard which never does.

**Refined open question for product:** does `bb functions publish`'s `function.json`-aware Block Store endpoint actually honor `"type": "Model"`/`"type": "Property"` and produce real native selectors for a third-party component (unlike the interactive wizard, which we've confirmed cannot) — or does the backend-side rendering gap described in the internal roadmap doc apply regardless of which path delivered `function.json`? This is now a concrete, testable question rather than a guess; not yet tested live (next step, pending time).

**RESOLVED, 2026-08-10 — confirmed live, definitively.** Set up a fresh `bb functions`-scaffolded WASM project (`marcel-tes/`), duplicated `store-file-base64` byte-for-byte from `block-store-wasm-components` (checksums verified identical to the upstream GitHub blob via `git hash-object`), and ran `bb functions login` + `bb functions publish` against the `marcel-tes` app. Result: the step appeared in the app's own "Wasm steps" palette tagged with a wrench icon and an **"Application specific"** tooltip — i.e. it landed as an app-local custom step, not a cross-app Block Store "dev block" (see the note below on what this reveals about `?type=wasm-function`'s actual behavior). Dragging it onto the canvas and opening its options: **MODEL rendered as a genuine "Select model" picker listing the app's real Data Models (Role, User, Webuser)** — not a "Select variable" synthetic-schema fallback. Selecting `Webuser`, **PROPERTY correctly adapted**: its property list showed all of Webuser's real properties (Created at, Email address, file, First name, Full name, Id, Last name) but only **`file` was selectable — every non-file/image property was greyed out**, exactly matching `function.json`'s `"allowedKinds": ["FILE","IMAGE"]` plus `"dependsOn": [{"option": "model", "action": "CLEAR"}]` behavior. Field labels and info tooltips (e.g. on FILE EXTENSION, FILE REFERENCE) also matched `function.json`'s `label`/`info` text exactly, unlike the wizard-uploaded version's generic auto-derived labels.

**Conclusion:** the platform gap was never "third-party components can't get native Model/Property selectors" — it was specifically that **the interactive "Add custom Wasm step" wizard discards `function.json` entirely**, so any option type that depends on `function.json`'s `meta.type` (Model, Property, Map, MultilineText, etc.) silently degrades to a generic WIT-shape fallback. `bb functions publish`, which does send `function.json` to the Block Store API, produces fully correct, working native selectors — the exact same UI real first-party steps get. This resolves every earlier finding in this log that concluded "not currently possible for third parties" — they were all specific to the wizard path, not a genuine platform ceiling.

**New open item this raises, worth reporting on its own:** the CLI-published component landed as an **app-scoped step**, not a Block Store "dev block" visible under My Blocks — meaning `?type=wasm-function` on `POST /blocks/publish` appears to register the component directly against the one application in the `ApplicationId` header, rather than into the shared, cross-app Block Store the way ActionsJS's `bb blocks publish` does (see `developer-learnings-log.md`'s CLI entry for the full ActionsJS-vs-WASM command comparison). Whether this is intentional (WASM Block Store distribution genuinely isn't rolled out yet) or a bug is unconfirmed — worth asking product directly rather than inferring further.

**Status:** RESOLVED — confirmed live via `bb functions publish`. The "app-scoped, not Block Store" behavior above is a new, separate open question worth its own report to product.

## Dragging a second custom Wasm step onto the canvas failed with "Failed to create action step" (2026-08-07)

**Observed:** while building a real test flow (`Start → Expression → Update Record → Slugify Text → Create Record (learning exercise) → Finish`), the first custom step (`Slugify Text`) was dragged onto the canvas, configured, and saved successfully with no issues. Immediately after, dragging the *second* custom Wasm step (`Create Record (learning exercise)`) onto the connector between `Slugify Text` and `Finish` produced a modal: *"Oops! Something went wrong — Failed to create action step. Refresh the page and try again."* The node visually appeared in the flow (with a warning triangle) despite the server-side creation failing — i.e., the canvas showed state that didn't actually exist yet.

**Why it matters:** two custom Wasm steps in the same flow may be hitting some kind of rate limit, ordering issue, or a bug specific to inserting a *second* custom-step node in one session; also a UX gap — the canvas rendering an unsaved/failed node as if it succeeded (before the refresh) could mislead an author into thinking it worked.

**How found:** during a real, hands-on flow-building exercise, immediately after successfully adding a first custom step to the same action.

**Status:** open — not yet reported to product devs. **Update, same session — isolated, confirmed twice independently.** Sequence of tests: (1) reproduced identically on a second attempt (refresh → same drag → same error) — deterministic, not transient. (2) Added a *second* `slugify-text` instance to the same flow instead — **that succeeded with zero errors.** This isolates the failure specifically to `create-record`, not "any second custom step in a flow." (3) Marcel independently reproduced the same `create-record`-specific failure in a different browser tab, unprompted — same conclusion reached two ways at once.

**Root cause found and confirmed via a controlled test.** Uploaded and tried adding `store-file-base64` (the official example, also import-bearing — 5 host imports total) as a step first: it worked perfectly on the first try, including the platform correctly auto-generating real **Model** and **Property** picker inputs directly from its WIT types (see the corresponding `developer-learnings-log.md` entry) — this ruled out "any import-bearing component fails" as the explanation, since a *more* complex import-bearing component worked fine. Comparing the WIT source of `create-record` (fails) against `store-file-base64`/`slugify-text` (both work) side by side, the one dimension unique to `create-record` was: **it uses the generic WIT world name `main` together with a host import.** `slugify-text` also uses `world main`, but has no imports. `store-file-base64` has imports, but uses a distinctly-named world (`world store-file-base64`), not `main`.

**Confirmed via a single-variable test**: renamed `create-record`'s WIT world from `main` to `create-record-world` (touching nothing else — same interface, same function signature, same single `data-api` import), rebuilt, re-uploaded as "Create Record v2", and it **added to the canvas successfully with zero errors** — first try. This isolates the bug precisely: **a Block Store component whose WIT world is named `main` and which also declares at least one host `import` fails to be added as an action step, even though it uploads/registers without error.** Components either without any import, or with an import but a non-`main` world name, work fine.

**Recommended fix for product**: either (a) make the platform robust to a world named `main` when imports are present, or (b) if `main` genuinely can't be supported with imports, surface a clear validation error at upload time instead of a generic "Failed to create action step" only when someone later tries to use the step.

**Correction, 2026-08-07:** the claim above that `store-file-base64` succeeded "including the platform correctly auto-generating real Model and Property picker inputs" was based only on the drag/upload completing without error, not on verifying what those inputs actually resolved to. Having since inspected them directly, they are **not** real Model/Property selectors — see the new "Open question: can third-party Wasm steps ever get real native Model/Property selectors?" entry below.

**Practical workaround for BB developers in the meantime**: logged in `developer-learnings-log.md` — always give your WIT world a distinct name (not `main`) if your component imports anything from the host.

## Third-party components have no path to a Map/key-value "Variables" editor like native steps get (2026-08-07)

**Observed:** native steps like `Expression` and `HTTP` render a genuine editable key-value table ("VARIABLES", KEY/VALUE columns, "+ Add" button) for options like `variables`/`headers`, even though the underlying WIT parameter for those options is a plain `string` (confirmed by reading `native-wasm-components`' own `http.wit`: `headers: json-string` — just a string alias, no special type). This table comes from `function.json` declaring `"type": "Map"` for that option — a purely `function.json`-driven UI, not something WIT types encode.

**Why it matters:** the only publish path available to third-party/Block Store component authors today — the "Add custom Wasm step" wizard in the app's Action Builder — was already confirmed earlier (see the `function.json`-is-not-read entry below) to skip `function.json` entirely and build the option form purely from WIT-type introspection. Since `"type": "Map"` is a `function.json`-only concept, **there is currently no way for a third-party component author to get this Map/Variables editor UI**, no matter how the WIT is shaped — confirmed directly by testing the one plausible WIT-level equivalent (`list<custom-record>`), which instead produces a "Select variable" schema picker (see the entry above), not an editable table.

**Concretely, for `create-record`**: its `fields` parameter is already the exact same shape as native HTTP's `headers` (a plain `string`) — the component isn't the limiting factor. The only way to reach the same nice UI native components get would be publishing through whatever internal pipeline reads `function.json` (the same one native components and the original `block-store-wasm-components` examples assume), which isn't available through the app's own IDE for third-party authors as far as we've found.

**Recommendation for product**: either make the interactive upload wizard read an uploaded `function.json` (at least for option types like `Map`/`MultilineText`/`Value` that aren't derivable from WIT alone), or document/expose whatever the actual third-party-accessible equivalent publish path is, if one exists.

**Status:** open — not yet reported to product devs. Confirmed with Marcel that no alternate publish path is known/available to test this against.

## Action canvas rendered empty after closing the "Add custom Wasm step" upload wizard (2026-08-07)

**Observed:** immediately after successfully saving a new custom Wasm step (`create-record`) through the 3-step upload wizard, the action editor canvas — which had a visible `Start → Expression → Update Record → Finish` flow before starting the upload — rendered completely empty (no nodes), and scrolling/panning didn't bring anything back. The step palette itself was fine (search, categories, the newly-added step all worked normally); only the canvas view was affected.

**Why it matters:** looks like a rendering state bug triggered by the upload-wizard-to-canvas transition, not necessarily a data-loss issue — but it's disorienting right after a successful upload, especially for a first-time component author who might reasonably assume the upload broke their existing action. Confirmed by Marcel as likely a minor bug worth flagging.

**Status:** open — not yet reported to product devs. **Update 2026-08-07 (first correction):** did not reproduce on a second upload (`slugify-text`, same action, same session) — the canvas stayed intact that time. **Second update, same day:** it then reproduced again on a *plain page reload/navigation* of the same action — no upload wizard involved at all this time. The step nodes were confirmed still present in the page's accessibility tree/DOM (`Start`, `Expression`, `Update Record`, `Finish` all found by an element search) — so this is a **pan/zoom position bug on load**, not data loss: the canvas's viewport just isn't restoring/computing a valid position to show the existing nodes. Standard remediation attempts (zoom out via the `-` control, a click-drag pan) did not bring the nodes back into view for automated interaction; a human with normal trackpad/mouse pan gestures may have better luck. **Reclassifying from "intermittent, low confidence" back up to "real, reproducible-enough-to-report" — happens independent of the upload wizard, on ordinary navigation.** **Workaround found (Marcel, same session):** navigating to a *different* action and then back into the affected one restores the canvas view correctly — a plain reload of the same URL does not. This points fairly specifically at a client-side state/mount bug (the canvas's pan/zoom-fit calculation likely only runs correctly on a fresh SPA route transition into the action, not on a hard reload of that same route) rather than a backend/data issue — useful detail for whoever picks this up on the product side.

## Uploading a custom Block Store component fails with an unhelpful "Internal Server Error" (2026-08-07)

**Observed:** uploading `slugify-text` (a minimal, verified-working, genuine `wasm32-wasip2` component — passes all unit/component tests, confirmed real component header) to the Block Store in production (my.bettyblocks.com) failed with a bare "Internal Server Error" — no further detail, no indication of which of the three uploaded artifacts (`.wasm`, `wit/world.wit`, `function.json`) caused it, no validation-style error message pointing at a specific field or file.

**Why it matters:** this makes it impossible for a component author to self-diagnose the problem — is it the `.wasm`, the WIT, the `function.json`, something about the specific model/values chosen at upload time, or a genuine platform bug? Without more detail, every failed upload is a dead end unless product/engineering can pull server-side logs.

**Status:** already reported directly to product devs by Marcel; no response yet as of 2026-08-07. Once product responds with a cause, update this entry and, if it turns out to be something upload-side authors can avoid, migrate the guidance to `developer-learnings-log.md` instead.

**Update 2026-08-07 — root cause substantially narrowed down, likely resolved: a stale/mismatched build artifact, not a WIT design issue.** Two things were tested in sequence:
1. `create-record` (a different, more complex component: host import, `serde_json`, `result<string, string>` return) uploaded with zero errors — ruling out "any custom component fails" as an explanation.
2. `slugify-text`'s own `.wasm` was rebuilt from the *same, unchanged source* on this machine (which had no Rust toolchain installed until earlier today) and re-uploaded. **It succeeded** — no error, registered as a real step, and — bonus data point — the "action canvas rendered empty" bug from the entry above did *not* reproduce this time.

The rebuilt binary is provably different from the original: same source, same `Cargo.lock`-pinned `wit-bindgen` version (0.58.0 both times), but a different SHA-256 hash and a different file size (64,764 vs. 71,669 bytes) — confirming the original `dist/slugify_text.wasm` was compiled in a different environment (most likely a different Rust/`wasm32-wasip2`-target toolchain version, since that's the one variable we can't verify was identical) than what's on this machine now. This lines up exactly with the upload page's own posted warning: *"Please ensure your Wasm component uses consistent WASI versions."*

**Practical implication for both audiences:** if an upload throws this bare "Internal Server Error" with no detail, rebuilding fresh with your current toolchain before assuming the component's *design* is at fault is a cheap, worthwhile first troubleshooting step. The `option<T>`-as-parameter hypothesis floated earlier is no longer the leading explanation, since the rebuilt `slugify-text` still uses `option<string>`/`option<u32>` and uploaded fine.

**Still worth reporting to product as feedback, even though this instance is resolved**: the error message itself gave zero indication that a WASI-version mismatch (or anything else) was the cause — a component author without a second, known-good component to compare against would have had no path to this diagnosis.
